# Sprint Conventions

These conventions are established from v0.1 through v0.3. The designer must
follow them when writing design.md.

## Document Formats

- Sprint plans: XML (sprint.xml). Generated by /new-sprint from design.md.
- Design documents: Markdown (design.md). Written by the designer.
- Execution logs: Markdown (log.md). Append-only. Written by the runner.
- Gate decisions: XML (gate.xml). Written by the commander.
- Mission blocks inside sprint.xml use CDATA sections for code-heavy content.

## Mission Grammar

Every mission has: context, objective, specification, steps, report.
Steps have: RUN (action), EXPECT (success criteria), FAIL (HARD or SOFT).
HARD fail stops the mission. SOFT fail is noted and continued.

## Tier Assignments

- **execute** (Sonnet-class): implementation, file modification, testing.
  The workhorse. Most missions are execute.
- **reason** (Opus-class): architectural judgment, gate decisions, ambiguity
  resolution. Used sparingly — only when the mission requires weighing
  tradeoffs or making design calls.
- **scout** (Haiku-class or nano): read-only audits, verification passes.
  Used for pre-flight checks and compliance scans.

## Review Flags

Missions with `review="true"` get a separate review task dispatched after
execution. The reviewer sees the executor's report and the original spec,
produces PASS / CONCERNS / FAIL with findings. CONCERNS is non-blocking.
FAIL requires a patch and re-review.

## Phase Structure

Each phase has a clear gate: all missions in the phase must be GREEN before
the next phase dispatches. Phase boundaries are where the sprint runner
pauses and reports status.

## Carry-Forward Tracking

Issues found during execution that are out of scope for the current mission
are logged as carry-forwards. The cleanup mission (typically last) addresses
them. Anything not resolved becomes a v(N+1) carry-forward item.

## Per-Mission Agent Termination (NEW for v0.4)

Each mission should be designed so its report contains everything the next
mission's agent needs. The runner dispatches one mission per agent context.
The agent executes, writes its report to log.md, and terminates. The next
agent reads: mission spec + risk review + pre-decisions + relevant log entries
from dependency missions. If an agent can't proceed from the log alone,
the log is insufficient — that's a design problem, not a runtime problem.

## Amendments

Numbered sequentially. State what changed and why. Issued by the commander
when a mission fails or a spec needs revision. Amendments are recorded in
log.md and applied to the affected mission before re-dispatch.

## Pre-Decisions

Ambiguities identified during design are resolved by the commander before
the sprint starts. Recorded as PD1, PD2, etc. in the sprint runner prompt.
Executors apply pre-decisions as stated — they don't re-decide.

## Known Exceptions

Design constraints that are intentionally violated. Blessed by the commander.
Documented with an ID (KE1, KE2) and referenced in the affected mission's
report.
