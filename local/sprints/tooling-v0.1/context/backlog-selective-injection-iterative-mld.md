# Backlog: Selective Principle Injection & Iterative MLD

Depends on: Origami reprocessing (MLD-compressed principles),
tooling-v1 complete.

## Selective Principle Injection

Every agent gets a tailored preamble — not the full manifesto.
The sprint planner decides which principles are relevant to each
mission. MLD has already compressed each principle to its minimum
lossless description. The preamble is assembled mechanically from
the compressed principles.

Implementation: a principle registry (SQLite or JSON) mapping
principle IDs to their MLD descriptions. The sprint planner
annotates each mission: "principles: [1, 3, 7]". The runner
assembles the preamble by looking up those IDs and concatenating
the compressed descriptions. The agent's context window contains
only the Origami it needs.

Benefits:
- Smaller preambles → cheaper cached prompts
- Relevant principles only → less noise, better adherence
- The sprint designer explicitly chooses which principles matter
  for each class of work
- A Wildebeest Mode executor doesn't know about documentation
  standards. A documentation agent doesn't know about Wildebeest
  Mode. Architectural incapacity through selective knowledge.

## Iterative Generation (Three-Draft Pattern)

Single Nano call produces three outputs at increasing refinement:

```
Prompt: "Generate a description for this function. Then rewrite
it shorter. Then rewrite into final form. Return all three as
structured output: {draft_1: str, draft_2: str, draft_3: str}"
```

10 calls × 3 drafts = 30 candidates for the cost of 10 calls.
One cache hit per call. The model does its own editorial pass
before returning.

MLD computation gets natural stratification:
- First drafts anchor the centroid (broadest semantic spread)
- Second drafts tighten it (self-edited, shorter)
- Third drafts sharpen it (final form, most refined)

Convergence can be computed within tiers and across tiers.
The best shortest, best medium, and best long get handed to
Opus for final selection: "Is the shortest sufficient? If not,
pick the medium. If not, pick the long."

## Gate Verb as Model Call

Replace the mechanical grammar filter with a model-judged gate.
Each proposed update gets a Nano call:

"Does this update adhere to the intent of the design description?
Respond with {valid: bool, reason: string}"

Five cents per million tokens. Structured output. The gate IS
the validation. Mechanical regex for obvious failures (empty
strings, non-UTF-8), model judgment for semantic compliance.

The validation chain for any file write:
1. Generate (Nano, iterative three-draft)
2. Converge (MLD geometric consensus)
3. Gate (Nano, "does this adhere to intent?")
4. Validate (Sonnet/Opus, final review if gate is uncertain)

Each step is a tailored Nano call with cached prompts except
step 4, which is the expensive judgment applied only to
uncertain cases.

## Batch Economics

Cloning a repo is parallelizable. Processing is parallelizable.
Summarizing is parallelizable. The entire pipeline:

1. Clone repo
2. Extract all functions (mechanical, parallel per file)
3. Generate descriptions (Nano batch, cached prompts)
4. Compute MLD convergence (numpy, parallel per function)
5. Summarize: descriptions → module summaries → repo summary
   (recursive summarization, each level is a batch call)
6. Validate summaries against descriptions (Nano batch)
7. Store everything in SQLite + vector store

If not time-sensitive: OpenAI batch API at 50% off. Submit the
entire repo as a batch job. Come back tomorrow. The recursive
summarization is itself batchable — each level's outputs become
the next level's inputs.

Total cost for a 500-function repo at batch pricing:
- Generation: 500 × 10 calls × ~200 tokens × $0.05/MTok = ~$0.05
- Embedding: ~10K tokens × $0.01/MTok = ~$0.0001
- Validation: 500 × $0.05/MTok = ~$0.001
- Summarization: ~50 module summaries + 1 repo summary = ~$0.01
- Total: under $0.10

At that price, re-index weekly. Re-index on every PR. Cost is
not a consideration.

## The Code We Generate

Code generated by this system is XML-tagged by default. Not for
the system's benefit — the system uses the database. The tags
are for casual human observers of the files. They can see the
section boundaries, read the descriptions, understand the
structure. The tags are a courtesy, not a dependency.

Source code that is not generated by this system is not touched.
The fork workflow: pull upstream, index locally, never modify
their files. The documentation lives in the local store. The
vectors live in the local store. The source is read-only.
